Implement inlining detection, docs/specs/relationships/05-inlining-detection.md and its details file (status proposed, 2026-11-01): a removed method or function whose body is mostly code added to a changed declaration is linked to it as an inlining, the reverse of extraction detection.

Background: extraction detection (declarations/05, docs/EXTRACTION-DETECTION.md) tiles an added declaration with the removed tokens of changed sources in ExtractionDetector. The details plan runs it once more with the sides swapped: a removed declaration tiled with the added tokens of changed targets, with the same thresholds (MIN_TOKENS 10, MIN_TILE 5, MIN_SHARE 0.65, MIN_REMOVED 0.75) and a shared MAX_WORK of 20 000 000 token pairs per file. Both passes write relationships (EXTRACT and INLINE) to the comparison result (relationships/02, ADR 0008); computed inlinedInto / inlinedFrom fields feed the outline. Labels: `inlined into <target>` on the removed declaration and `code inlined from <declaration>` on the target, up to 3 names then `+N more`; the summary line counts `inlined` instead of `removed`; hiding removed changes hides inlinings. The spec was written before relationships/02 and 03 were implemented and before rename grouping, so parts of it may no longer match the code.
